# План реализации продвинутого бота («умный» уровень)

Документ отвечает на issue #26: **сначала договариваемся о структуре и логике**,
и только потом пишем код. Здесь зафиксировано:

1. что уже есть в репозитории (без догадок — по коду `main`);
2. какая архитектура предлагается (интерфейс бота, память, план игры);
3. как именно бот «запоминает» карты и что делает в каждой ситуации;
4. как это показывается в UI (выбор уровня + объяснения ходов в логе);
5. **поэтапный план работ, разбитый на готовые issue** с критериями приёмки и тестами.

Уроки из issue #24 и #25 учтены отдельным разделом «Почему прошлые попытки провалились».

## 0. Краткие цели (что считаем успехом)

| # | Цель | Как проверяем |
|---|------|---------------|
| G1 | Есть второй уровень бота, который **анализирует стол и помнит карты** | код + юнит-тесты памяти |
| G2 | Умный бот **статистически сильнее** простого | `botMatch`: доля «дурака» у smart ≤ 45 % в дуэли на 1000 партий (при 50 % у равных) |
| G3 | **Выбор уровня бота в лобби** (локальный клиент, потом сеть) | руками в браузере + чек-лист |
| G4 | **Переключатель «объяснять ходы»**, объяснения падают в лог партии | руками в браузере + CLI `--verbose` |
| G5 | Ничего не сломано в движке и простом боте | CI (`simulate`, `playVerbose`, smoke) зелёный |
| G6 | Правки сделаны **сначала в локальном клиенте**, сеть — отдельным шагом | порядок issue (этапы 1–5 → этап 6) |

> Важно: G2 — это **условие мержа**. Если умный бот не выигрывает у простого на длинной
> дистанции — уровень не выпускаем, а чиним эвристики (в #24 первая версия проигрывала
> простому боту: 59 % «дурака» против 37 %).

### Формат состояния, который бот получает от движка

`game.getState(botId)` (`src/game.js:168`) возвращает:

```js
{
  phase,                 // 'need-attack' | 'defender-to-act' | 'finished'
  trumpSuit, trumpCard,
  talonCount,            // сколько карт осталось в прикупе
  discardCount,          // сколько ушло в бито
  table: [{ attack, defense }],
  tableGoingToDefender,  // защитник уже сказал «беру»
  attacker, defender,    // id игроков
  players: [{ id, name, handCount, out, finishRank, hand? }], // hand только у себя
  durak, finished,
}
```

### Формат действий (`getLegalActions`)

```js
{ type: 'attack',   card }            // ходить/подкинуть
{ type: 'defend',   card, against }   // отбиться card от against
{ type: 'transfer', cards: [...] }    // перевод
{ type: 'take' }                      // забрать
{ type: 'pass' }                      // бито/пас
```

### Две известные проблемы локального клиента (их обязательно чиним)

1. **Боту подсовывают урезанное состояние.** В `visual/index.html` (и его копии `docs/index.html`,
   строки ~1191 и ~1260) бот получает не `game.getState(id)`, а самодельный объект:
   ```js
   const stateForBot = { trumpSuit, talonCount, players: game.players.map(pl => ({ id: pl.id, hand: pl.hand })) };
   ```
   Здесь **нет `table`, `discardCount`, `attacker`/`defender`, `handCount`, `phase`** — умный бот
   на таком состоянии физически не может анализировать стол. Это первое, что нужно исправить.
2. **Боты видят руки всех игроков** (в объекте выше отдаются полные `hand` всех). Для умного бота
   это не просто «читерство» — это делает бессмысленной саму память о картах. Бот обязан получать
   **маскированное** состояние (`getState(botId)`), иначе метрики G2 недостоверны.

### Дубликат `visual/index.html` ↔ `docs/index.html`

Файлы идентичны (`docs/` — это GitHub Pages). Любая правка клиента должна попадать в оба,
поэтому в план включён шаг «скрипт синхронизации + проверка в CI», чтобы копии не разъезжались
(в #25 их правили вручную, и это главный источник расхождений).

## 3. Архитектура

### 3.1. Интерфейс бота

Простой бот сегодня — чистая функция `(state, playerId, legalActions) -> action`. Умному нужна
**память между ходами**, поэтому вводим «мозг» (объект с состоянием), а старый API сохраняем.

```js
// src/bots/index.js
export const BOT_LEVELS = [
  { id: 'simple', label: 'Простой',              description: 'Базовые эвристики, ничего не запоминает' },
  { id: 'smart',  label: 'Умный (считает карты)', description: 'Помнит вышедшие карты, анализирует стол, объясняет ходы' },
];
export const DEFAULT_BOT_LEVEL = 'simple';

export function normalizeBotLevel(x) { /* неизвестное -> DEFAULT_BOT_LEVEL */ }
export function botLevelLabel(id)    { /* 'Простой' | 'Умный (считает карты)' */ }

// Фабрика "мозга" — один экземпляр на одно место за столом, живёт всю партию.
export function createBotBrain(level, options = {}) {
  return {
    level,
    reset(),                                   // новая партия
    observe(state, playerId),                  // впитать наблюдения (вызывается перед decide)
    decide(state, playerId, legalActions)      // -> { action, reason?, analysis? }
  };
}
```

Правила совместимости:

* `simpleBotDecide` остаётся экспортированным из `src/bots/simpleBot.js` **без изменения поведения**
  (на нём висят `simulate.js`, `playVerbose.js`, `smoke.js`, `server/rooms.js` и клиент);
* «мозг» уровня `simple` — тонкая обёртка: `decide()` возвращает `{ action: simpleBotDecide(...) }`;
* `decide()` **всегда** возвращает объект; вызывающий код берёт `.action`, а `.reason`/`.analysis`
  пишет в лог только если включены объяснения.

### 3.2. Где живёт код

```
src/bots/
  simpleBot.js     (не трогаем логику)
  memory.js        (новое) — CardTracker: память о картах
  analysis.js      (новое) — чистые функции оценки: beats, canBeat, оценка руки, план защиты
  smartBot.js      (новое) — политика решений, собирает reason/analysis
  index.js         (новое) — реестр уровней + createBotBrain
src/cli/
  botMatch.js      (новое) — очный матч уровней, статистика + verbose-лог объяснений
```

Разделение `memory / analysis / smartBot` нужно, чтобы память и оценки покрывались юнит-тестами
отдельно от «вкусовых» эвристик.

## 4. Как бот «запоминает» карты (`CardTracker`)

### 4.1. Что вообще можно знать честно

Бот видит только то, что видит живой игрок: свою руку, стол, количество карт у других, размер
прикупа и бито, а также **всё, что происходило раньше** (карты, которые лежали на столе).
Отсюда модель знаний:

```
ВСЕ КАРТЫ КОЛОДЫ = моя рука
                 ∪ карты на столе сейчас
                 ∪ бито (ушли в отбой)
                 ∪ карты, точно забранные конкретным соперником
                 ∪ козырь под колодой (известен: state.trumpCard)
                 ∪ НЕИЗВЕСТНОЕ (прикуп + скрытые руки соперников)
```

### 4.2. Структура состояния трекера

```js
class CardTracker {
  constructor(deckSize, trumpSuit, trumpCard, meId, playerIds)
  all            // Set<cardKey> — полная колода, cardKey = `${rank}${suit}`
  discard        // Set<cardKey> — ушли в бито (точно вне игры)
  onTable        // Set<cardKey> — лежат на столе сейчас
  takenBy        // Map<playerId, Set<cardKey>> — карты, которые игрок ЗАБРАЛ со стола
  seenPlayed     // Map<playerId, Set<cardKey>> — какие карты игрок уже выкладывал (история)
  voidSuits      // Map<playerId, Set<suit>>    — масти, которых у игрока точно нет
  trumpCard      // карта под колодой — уйдёт последнему добирающему
}
```

### 4.3. Как трекер обновляется

Память обновляется **наблюдением за сменой состояний**: перед каждым решением бот получает свежий
`state`, а трекер сравнивает его с предыдущим снимком (`observe(state)`):

| Событие (как определяется) | Что записываем |
|---|---|
| На столе появилась новая карта-атака | `onTable += card`; автор хода = `state.attacker`/очередь подкидывания → `seenPlayed[author] += card` |
| На столе появилась карта-защита | `onTable += card`; `seenPlayed[defender] += card` |
| Стол опустел, `handCount` защитника **не вырос** | все карты стола → `discard` |
| Стол опустел, `handCount` защитника **вырос** на размер стола (или был `tableGoingToDefender`) | все карты стола → `takenBy[defender]` (и остаются «известными в его руке», пока он их не сыграет) |
| `talonCount` уменьшился | у игроков прибавились **неизвестные** карты (кроме случая ниже) |
| `talonCount === 0` и кто-то добрал последнюю карту | это `trumpCard` → она известна: `takenBy[thatPlayer] += trumpCard` |
| Защитник взял, хотя на столе была карта масти X, которую он мог бы побить | `voidSuits[defender] += X` (эвристика «нечем бить»), с поправкой на нежелание тратить козырь |
| Игрок спасовал при подкидывании | у него, скорее всего, нет карт рангов со стола → мягкий признак (**вероятностный**, хранится отдельно от «точных» фактов) |

Разделяем **точные** факты (`discard`, `takenBy`, `onTable`) и **предположения**
(`voidSuits`, «спасовал → нет ранга»). В объяснениях они формулируются по-разному
(«знаю», «скорее всего»).

### 4.4. Что трекер отдаёт наружу (API)

```js
unknownCards()                  // карты, которые могут быть у соперников или в прикупе
opponentPossibleCards(oppId)    // карты-кандидаты в руке соперника
opponentKnownCards(oppId)       // карты, которые он точно держит (забрал и не сыграл)
isOpponentHandCertain(oppId)    // true, если прикуп пуст и handCount == размеру known-множества
probabilityOpponentHas(card)    // грубая оценка: 1/N по неизвестным (для эндшпильных решений)
highestRemaining(suit)          // самая старшая невышедшая карта масти
trumpsLeftOutside(myHand)       // сколько козырей ещё не у меня и не в бито
```

Главный практический смысл: **в эндшпиле** (`talonCount === 0`) множество неизвестных схлопывается,
и при двух игроках рука соперника становится полностью просчитанной → бот может играть точно.

## 5. Анализ и «план игры»

### 5.1. Базовые функции (`analysis.js`, чистые, без состояния)

```js
beats(defCard, atkCard, trumpSuit)       // строго по правилам движка
cardPower(card, trumpSuit)               // числовая ценность карты
handStrength(hand, trumpSuit, tracker)   // сколько козырей, сколько «непобиваемых», средний ранг
planDefense(table, hand, trumpSuit)      // можно ли отбить ВЕСЬ стол и какой минимальной ценой
unbeatableCards(hand, trumpSuit, tracker)// карты, которые соперник уже ничем не побьёт
suitControl(hand, suit, tracker)         // держу ли я старшую невышедшую в масти
```

### 5.2. Фазы партии и цель в каждой

| Фаза | Условие | Цель бота |
|---|---|---|
| **Дебют** | `talonCount > handSize * активных игроков` | Сливать мелочь, не тратить козыри, собирать пары/тройки одного ранга для подкидывания |
| **Миттельшпиль** | прикуп тает | Считать козыри, ловить моменты «вынудить взять», следить, чтобы не остаться с мусором |
| **Эндшпиль** | `talonCount === 0` | Точный расчёт: избавиться от карт; при известной руке соперника — считать до конца |

Итог фазы + оценка руки = «план», который бот прикладывает к каждому объяснению
(`analysis`: «эндшпиль, у меня 2 козыря, соперник держит K♠ и 9♦»).

### 5.3. Политика решений

**Ход/подкидывание (`attack`):**

1. Если могу **добить**: у соперника мало карт и у меня есть карта, которую (по памяти) он не бьёт → бросаю её.
2. Подкидываю по возрастанию ценности, предпочитая ранги, которых **много в руке** (разгрузка парами).
3. Не подкидываю козырь и старшую в масти, пока идёт прикуп **и** рука не перегружена.
4. Учитываю лимит стола и `handCount` защитника: если он уже не отобьётся — грузим до предела.
5. В эндшпиле приоритет — **избавиться от карт**, придерживание почти отключается.
6. Не оставляю себе «мусор, который никому не подкинешь» (одиночные мелкие карты мёртвой масти).

**Защита (`defend` / `take` / `transfer`):**

1. `planDefense`: если стол **целиком** не отбивается и неотбитых ≥ 2 — берём сразу, не разбазаривая карты
   (в игре 3+ проверяем отдельно: там состав стола ещё меняется).
2. Бьём минимальной достаточной картой; козырь — только если некозырной нет.
3. Перевод — если он дешевле защиты (не отдаём козырь) и у следующего игрока много карт.
4. Не жжём крупный козырь (K/A) ради мелкой карты, когда прикуп ещё есть и взятие дёшево.
5. В просчитанном эндшпиле сравниваем два исхода (отбиться vs взять) прямым перебором на 1–2 хода вперёд.

**Пас (`pass`):** пасуем, когда подкидывание вредит (ломает пары, отдаёт козырь, кормит соперника,
который скоро выйдет).

Каждое правило — **отдельный именованный флаг** в профиле бота, чтобы A/B-тестировать его вклад:

```js
const SMART_PROFILE = {
  holdTrumpsWhileTalon: true,
  finishOffWeakOpponent: true,
  takeWhenTableUnbeatable: true,
  exactEndgame: true,
  dumpPairs: true,
};
```

## 6. Объяснения ходов

`decide()` возвращает:

```js
{
  action,                 // то, что уходит в applyAction
  reason:   'подкидываю 9♦ — у соперника 1 карта, и 9♦ он по моим подсчётам не бьёт',
  analysis: 'эндшпиль: прикуп пуст, у меня 3 карты (2 козыря), соперник держит K♠, 9♦',
}
```

Формат строк в логе партии (одинаковый в локальном клиенте, CLI и на сервере):

```
🤖 Бот 2: подкидываю 9♦ — у соперника 1 карта, и 9♦ он по моим подсчётам не бьёт
   └ расклад: эндшпиль, прикуп пуст, соперник держит K♠, 9♦
```

Правила:

* объяснения пишутся **только** при включённом флаге `botExplain`;
* тексты на русском, без внутренних терминов кода;
* строка `analysis` необязательна и пишется отдельной строкой с отступом;
* объяснение не должно раскрывать то, чего бот «не знает» (нельзя печатать чужие руки,
  если они не выведены из памяти) — иначе это подсказка игроку и утечка информации.

Изменения в логике страницы:

1. завести `botBrains` — по «мозгу» на каждого бота, создавать в `startInteractiveGame()`;
2. в `scheduleBotStep()` передавать боту **`igame.getState(turnPlayer.id)`** вместо самодельного
   `stateForBot` (см. проблему 1 и 2 в разделе 1);
3. если `botExplain` включён — дописывать `🤖 …` в `igame.log`, чтобы объяснение попало
   в `renderFullLog()` вместе с событиями движка;
4. смена уровня применяется со следующей партии (кнопка «Новая партия»), чтобы не ломать
   уже накопленную память.

### 7.2. Синхронизация двух копий клиента

`npm run sync-client` — копирует `visual/index.html` → `docs/index.html`, а шаг в CI
проверяет, что файлы совпадают (`cmp -s`), иначе падает. Больше никаких ручных
двойных правок.

### 7.3. Сетевая версия — **только после приёмки локальной**

`server/rooms.js` (`botLevel`, `botExplain`, «мозг» на место, объяснения в лог комнаты),
`server/index.js` (поля в `createRoom`/`addBot`/`fillWithBots`, сообщения `botOptions`, `botLevels`),
`server/test-client.html` (селект + чекбокс + обработчики).

| Юнит | `CardTracker`: бито/взятие/добор/эндшпиль-расчёт | `test/memory.test.js` (node:test) |
| Юнит | `analysis.js`: `beats`, `planDefense`, `unbeatableCards` | `test/analysis.test.js` |

| Регресс | `simulate` (0 ошибок движка), `playVerbose`, `npm run smoke` | CI |
| Ручной | локальный клиент: оба уровня × объяснения вкл/выкл | чек-лист в PR |

`botMatch.js` (этап 1) печатает: число партий, конфигурацию, ошибки движка, зависания, ничьи,
долю «дурака» по местам; с `--verbose` — лог одной партии вместе с объяснениями.
Чтобы исключить перекос по местам, матч гоняется **в обе стороны** (smart на 1-м и на 2-м месте).

## 10. Риски и как их гасим

| Риск | Мера |
|---|---|
| Умный бот слабее простого (как в #24) | Бенчмарк раньше кода; правило мержа G2; A/B по каждому флагу |
| Расхождение `visual/index.html` и `docs/index.html` | Скрипт синхронизации + проверка в CI |
| Бот «подглядывает» в чужие руки | Передаём только `getState(botId)`; отдельный тест-инвариант |
| Память ломается на 3+ игроках | Отдельные тесты и прогоны на 3/4/6 игроков; при неопределённости бот деградирует к простым эвристикам, а не к ошибочным выводам |
| Огромные нечитаемые PR | По одному этапу на PR, файлы этапа перечислены заранее |
| Объяснения спамят лог | Флаг `botExplain` по умолчанию **выключен**; одна строка на ход + необязательный `analysis` |
