# Issue #71: профиль поиска и локальный Worker

## Область изменений и порядок ревью

Изменения собраны в ветке `openai-gpt-6-astra-issue-71` отдельными коммитами:
1. Воспроизводимый профиль и исходные артефакты.
2. Стабильная сортировка ходов, изоляция таблицы и кеши одного решения.
3. Worker, исходный клиент, штатная сборка и регрессии.

Новый компактный backend и matching/DP для `planDefense` не вводились.
Политика SmartBot и флаги профиля не менялись. При нескольких равнозначных
оптимальных ходах допустим другой ход из множества оптимальных; на проверенных
малых позициях совпали также `bestActions`. При лимите времени число просмотренных
узлов зависит от машины, поэтому совпадение недоказанных результатов не обещается.

## Методика и сырые данные

`scripts/profile71.mjs`: три фиксированные позиции (small-win, small-defense,
audit64), каждая с переводом и без; полные позиции сохранены в JSON.
12 повторов каждой, одинаковый прогрев (1000 узлов), измеряемый бюджет
400000 узлов / 2000 мс. Записываются все решения, легальные ходы, узлы,
таймауты, задержки, p50/p95/p99 и суммарные узлы / суммарное время.
CPU sampling и heap allocation sampling Inspector (интервал 32768 байт)
включены одновременно: это инструментированные измерения, не чистый benchmark.
Heap sampling — статистическая оценка, не полный журнал всех аллокаций.

Артефакты: `bench/issue71-{before,after}.{json,cpuprofile,heapprofile}`.
**Первоначальные before/after оказались на разных облачных CPU**
(EPYC 9V74 и EPYC 7763). Разницу 88–91 против 138–139 тыс. узлов/с
нельзя приписывать оптимизации. Эти сырые данные оставлены для прозрачности.

Для корректного сравнения дополнительно последовательно выполнены обе версии
на одной машине: `bench/issue71-samehost-{before,after}.{json,cpuprofile,heapprofile}`.
Linux x64, EPYC 7763, Node 20.20.2 / V8 11.3.244.8-node.38;
точные ревизии записаны в JSON. Исходная версия — `57d014785d674297445c175b024a0564312918cd`
(скрипт профиля уже добавлен, изменения решателя ещё не внесены).

### Результаты на одной машине

Задержки в мс; p95 и p99 при 12 повторах оба равны максимуму выборки.
Этой выборки недостаточно для надёжной оценки хвостов в production.

| Сценарий | p50 до → после | p95/p99 до → после | узлов/с до → после | таймауты до/после |
|---|---:|---:|---:|---:|
| small-win, без перевода | 0.062 → 0.061 | 0.299 → 0.251 | 32091 → 34138 | 0 / 0 |
| small-win, с переводом | 0.026 → 0.029 | 0.096 → 0.122 | 83627 → 73317 | 0 / 0 |
| small-defense, без перевода | 0.159 → 0.201 | 1.292 → 0.510 | 138922 → 171077 | 0 / 0 |
| small-defense, с переводом | 0.196 → 0.177 | 2.451 → 0.759 | 83474 → 166460 | 0 / 0 |
| audit64, без перевода | 2000.191 → 2000.118 | 2001.149 → 2000.228 | 136240 → 139731 | 100% / 100% |
| audit64, с переводом | 2000.108 → 2000.184 | 2001.868 → 2000.761 | 135090 → 136342 | 100% / 100% |

Итого: на сложных позициях наблюдаемая разница throughput всего около 2.6% / 0.9%,
не доказанное универсальное ускорение. Латентность остаётся около двух секунд,
все сложные позиции достигают лимита. Главный выигрыш для UI — перенос вычислений
из главного потока, а не сокращение времени поиска.

В исходном CPU-профиле заметны рекурсивный `search` и GC (3541 self samples GC).
Выбрано консервативное сокращение временных объектов сортировки с сохранением
стабильного порядка; clone, строковые ключи и движок переходов не переписывались.
Профиль не доказывает необходимость замены `planDefense` на DP.

## Безопасность кешей

- `options.table` очищается при каждом решении. Межходового использования оценок
  нет: ключ позиции не кодирует правила, козырь и корневого игрока.
- Анализ известной руки и непробиваемых карт переиспользуется только в пределах
  одного `decide`; `finally` удаляет кеш и при исключении.
- Нет долгоживущего кеша `outsideCards` и нет зависимости от устаревшей памяти.
- Регрессии покрывают разные правила, козыри и корни, повторные решения,
  изменение наблюдений и очистку после ошибки.

## Worker и контракт

`src/bots/workerBrain.js` содержит адаптер сообщений и обработчик мозга.
В Worker отправляются маскированные состояния, свои легальные действия и
упорядоченные публичные наблюдения. Мозг живёт между решениями одной партии,
а не создаётся на каждый ход. Тесты сравнивают наблюдения и память с синхронным
мозгом и проверяют отсутствие приватных карт в контракте.

`scripts/build-client.mjs` собирает код в Blob Worker для автономного HTML.
Изменения внесены в `client/template.html`; `docs/index.html` и
`visual/index.html` сгенерированы штатной сборкой.

Новая партия отменяет ожидающие решения и завершает Worker. Поколение партии
и ID запросов не позволяют применить устаревший ответ. Ошибки Worker приводят
к безопасному откату на простого бота, а не синхронному тяжёлому поиску.
Worker завершаются и при окончании партии. Во время асинхронной подготовки
недоступно управление просмотром ещё не готовой истории.

## Проверки

- `npm test`: 172/172, без пропусков.
- Сырые same-host результаты автоматически сопоставлены: сценарии идентичны,
  все решённые малые позиции сохранили `value` и `bestActions`, ноль нелегальных
  ненулевых действий. `action: null` у неразрешённого поиска не считается ходом.
- `test/workerBrain.test.js`: маскирование, порядок наблюдений, ошибки,
  отмена/рестарт и устаревшие ответы, контексты таблицы и кеши.
- Chromium 153.0.8010.12, `scripts/check-worker71.mjs`:
  121 animation frame и 202 тика таймера за 2014.7 мс тяжёлого решения,
  синхронное и Worker-решение SmartBot совпали, отмена и рестарт прошли,
  оставшихся workers 0, ошибок страницы 0.
  Сырой результат — `bench/issue71-browser.json`.
  Чтобы быстрый браузер гарантированно работал около двух секунд, только
  тестовый вход тяжёлого Worker использует 4000000 узлов / 2000 мс.
  Production-бюджет не увеличен. Это проверка отзывчивости, не сравнение
  производительности Node и Chromium.

## Воспроизведение

Из корня checkout ветки, Node 20:

```sh
npm ci
npm run build-client
npm test

# Около минуты на каждый инструментированный профиль.
git worktree add --detach /tmp/issue71-before 57d014785d674297445c175b024a0564312918cd
(cd /tmp/issue71-before && REPEATS=12 node scripts/profile71.mjs bench/recheck-before)
REPEATS=12 node scripts/profile71.mjs bench/recheck-after
# Сравнивать на одной машине без параллельной нагрузки.
# До удаления worktree сохраните /tmp/issue71-before/bench/recheck-before.*
git worktree remove --force /tmp/issue71-before

# Браузерная проверка, зависимость не добавляется в production.
npm install --prefix /tmp/worker71 --no-save playwright@1.63.0
/tmp/worker71/node_modules/.bin/playwright install chromium
PLAYWRIGHT_MODULE=/tmp/worker71/node_modules/playwright/index.mjs node scripts/check-worker71.mjs
```

В минимальном Linux могут понадобиться системные зависимости Chromium
(`playwright install --with-deps chromium`). Профили можно загрузить в Chrome
DevTools: CPU profile и Memory / allocation sampling. Скрипт браузерной проверки
сам запускает HTTP-сервер, делает assertions и закрывает сервер и браузер.
