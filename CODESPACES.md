# Тестовый запуск проекта в GitHub Codespaces

Пошаговая инструкция: как за несколько минут поднять проект в облачном
Codespaces, проверить движок, ботов, WebSocket-сервер, реконнект и визуализацию,
и как дальше его дорабатывать.

Ничего локально ставить не нужно: браузер + аккаунт GitHub.

---

## 0. Что вообще есть в проекте

| Часть | Файлы | Как проверяется |
|---|---|---|
| Движок правил | `src/game.js`, `src/deck.js`, `src/rules.js` | CLI-скрипты (шаг 2) |
| Боты | `src/bots/simpleBot.js` | CLI-скрипты (шаг 2) |
| CLI-прогон партии | `src/cli/playVerbose.js`, `src/cli/simulate.js` | `npm run play`, `npm run simulate` |
| WS-сервер + комнаты | `server/index.js`, `server/rooms.js` | `npm run server` (шаг 3) |
| Тестовый клиент сервера | `server/test-client.html` | открывается на `/` (шаг 4) |
| Визуализация (боты / игра против ботов) | `docs/index.html` = `visual/index.html` | открывается на `/visual` или как файл |

Единственная зависимость — пакет `ws` (нужен только серверу). CLI-скрипты
работают вообще без `npm install`.

## 1. Создать Codespace

1. Откройте репозиторий на GitHub.
2. Кнопка **Code** → вкладка **Codespaces** → **Create codespace on main**.
3. Подождите 1–2 минуты, пока поднимется контейнер: в репозитории есть
   `.devcontainer/devcontainer.json` (Node 20), поэтому `npm install`
   выполнится автоматически (`postCreateCommand`), а порт **8080** будет
   проброшен заранее.
4. Откроется VS Code в браузере. Нижняя панель → вкладка **TERMINAL**.

Проверьте окружение:

```bash
node -v      # ожидается v20.x (минимум v18 — используется ESM и node:fs/promises)
npm -v
```

Если Codespace создавался до появления devcontainer-файла (или вы работаете
локально), выполните вручную:

```bash
npm install
```

## 2. Проверить движок и ботов (без сети, без UI)

### 2.1. Подробный лог одной партии

```bash
node src/cli/playVerbose.js 2 24      # 2 игрока, колода 24
node src/cli/playVerbose.js 4 36      # 4 игрока, колода 36
node src/cli/playVerbose.js 6 52      # 6 игроков, колода 52
```

Или коротко пресетом из `package.json`: `npm run play` (= `2 24`).

Что смотреть в выводе:
- блок `--- Начальные руки ---` — у каждого по 6 карт;
- `--- Лог партии ---` — по шагам: атака, защита, перевод, отбой/взятие,
  добор из колоды;
- `--- Итог ---` — порядок выхода, кто «дурак», число шагов симуляции.

⚠️ Если в конце появилась строка
`!! Достигнут предохранитель по числу шагов` — партия зациклилась.
Это известная редкая проблема (см. README, п.5 «Известные упрощения»).
Сохраните вывод и заведите отдельный issue.

### 2.2. Массовый прогон на стабильность

```bash
node src/cli/simulate.js 1000 2 24
node src/cli/simulate.js 500 4 36
node src/cli/simulate.js 300 6 52
```

Или `npm run simulate` (= `1000 2 24`).

Ожидаемый результат — строка `Ошибок движка: 0`.
Ненулевые `Зависших (упёрлись в предохранитель)` и заметный процент `Ничьих`
на 3+ игроках — известное поведение, описанное в README.

Быстрый прогон всех комбинаций сразу:

```bash
for p in 2 3 4 5 6; do for d in 24 36 52; do
  echo "=== players=$p deck=$d ==="; node src/cli/simulate.js 200 $p $d | head -3;
done; done
```

## 3. Запустить сервер мультиплеера

```bash
npm run server
# -> Durak WS-сервер слушает порт 8080
```

Порт можно поменять: `PORT=3000 npm run server`.

Полезные переменные окружения (см. `server/rooms.js`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PORT` | `8080` | порт HTTP + WebSocket |
| `BOT_TAKEOVER_MS` | `30000` | через сколько мс после разрыва связи игрока подменяет бот |
| `BOT_MOVE_DELAY_MS` | `700` | пауза между ходами бота |
| `ROOM_CLEANUP_GRACE_MS` | `60000` | через сколько удаляется опустевшая комната |
| `ROOM_SWEEP_INTERVAL_MS` | `10000` | как часто проверяются пустые комнаты |

Для быстрой проверки подмены ботом удобно так:

```bash
BOT_TAKEOVER_MS=3000 BOT_MOVE_DELAY_MS=200 npm run server
```

## 4. Открыть тестовый клиент в браузере

После старта сервера Codespaces сам покажет всплывашку
**«Your application running on port 8080 is available»** → **Open in Browser**.
Если всплывашка пропала: панель **PORTS** → строка `8080` → иконка глобуса
(**Open in Browser**) либо скопируйте URL вида
`https://<имя-codespace>-8080.app.github.dev`.

По этому адресу сервер отдаёт:

- `/` — **тестовый клиент** (`server/test-client.html`);
- `/visual` — офлайн-визуализацию (`docs/index.html`);
- `/health` — служебный JSON `{"ok":true,...}` для проверки, что сервер жив.

Поле **«Подключение»** в тестовом клиенте подставляется автоматически
(`wss://<ваш-хост>` в Codespaces, `ws://localhost:8080` при открытии файла
локально) — просто нажмите **Подключиться**, статус должен стать «подключено».

> Если WebSocket не подключается из внешнего браузера — проверьте видимость
> порта: панель **PORTS** → правый клик на `8080` → **Port Visibility** →
> **Public**. По умолчанию порт приватный и доступен только вам (по вашей
> сессии GitHub), что нормально для одиночного теста, но мешает позвать
> второго игрока с другого аккаунта.

## 5. Сценарии ручного теста сервера

### 5.1. Партия на двоих (две вкладки)

1. Вкладка A: **Создать комнату** → имя, 2 игрока, колода 24 → **Создать**.
   В логе появится код комнаты (5 символов, например `K7QP2`).
2. Вкладка B: откройте тот же URL, **Подключиться** → **Присоединиться по коду**
   → введите код + имя → **Войти**.
3. Как только мест не осталось, партия стартует: у обеих вкладок появляются
   руки, стол и подсвеченные зелёным допустимые действия.
4. Играйте по очереди. Проверяйте:
   - подсвечиваются только легальные действия (сервер сам считает
     `getLegalActions`, клиент ничего не додумывает);
   - чужие карты не видны (в `state` они приходят только числом);
   - «взять» / «бито» / перевод отрабатывают, лог партии совпадает у обоих.

### 5.2. Лобби

- В соседней вкладке (не входя в комнату) нажмите **Обновить список** —
  комната видна со своими правилами.
- Список должен обновляться сам при создании/заполнении/старте/удалении комнаты.
- Выход из ещё не начавшейся комнаты — кнопка **Выйти из комнаты (leave)**.
  Из начатой партии выйти нельзя — сервер вернёт ошибку, это ожидаемо.

### 5.3. Реконнект и подмена ботом

1. Запустите сервер с `BOT_TAKEOVER_MS=5000`.
2. Начните партию на двоих, затем во вкладке B нажмите
   **Оборвать соединение (имитация разрыва сети)**.
3. Ожидание: ~5 секунд партия стоит, потом за отключившегося начинает
   ходить бот, а вкладка A продолжает играть как ни в чём не бывало.
4. Во вкладке B нажмите **Переподключиться (rejoin)** — вы возвращаетесь
   на своё место, состояние приходит целиком, бот отключается.
5. **Забыть сохранённую сессию** — очищает `localStorage` (тест «нового игрока»).

### 5.4. Комната с ботами / на 3+ игроков

Создайте комнату на 3–6 игроков и подключите столько же вкладок, либо
проверьте, как места добираются ботами после таймаута отключения.

## 6. Визуализация без сервера

`docs/index.html` (и идентичный `visual/index.html`) — самодостаточная
страница, серверу не нужна:

- в Codespaces: откройте `/visual` на проброшенном порту 8080;
- либо правый клик по `docs/index.html` в дереве файлов → **Download** и
  откройте локально;
- либо поднимите отдельную статику: `npx serve docs` (порт тоже пробросится).

Внутри два режима: просмотр партии ботов и «играю против ботов» с открытыми
картами для отладки.

## 7.1. Одна команда для проверки всего (и для внешних инструментов)

```bash
bash /workspaces/durakProekt/scripts/codespace-check.sh
# или из корня репозитория:
npm run check
```

Скрипт `scripts/codespace-check.sh` повторяет весь набор проверок из CI
(версии, `playVerbose`, `simulate` на четырёх конфигурациях, `/health`, `/`,
`/visual`, `npm run smoke`) и **сам определяет корень репозитория**, поэтому
его можно запускать из любого каталога.

Это важно при запуске команд снаружи, через `gh`:

```bash
gh codespace ssh -c <имя-codespace> -- 'bash /workspaces/durakProekt/scripts/codespace-check.sh'
```

Обратите внимание: `gh codespace ssh` стартует команду в домашнем каталоге
(`/home/node`), а не в `/workspaces/durakProekt`. Поэтому «голый»
`npm run smoke` через SSH падает так:

```
npm error code ENOENT
npm error path /home/node/package.json
```

Правильные варианты:

```bash
gh codespace ssh -c <имя> -- 'cd /workspaces/durakProekt && npm run smoke'
gh codespace ssh -c <имя> -- 'npm --prefix /workspaces/durakProekt run smoke'
gh codespace ssh -c <имя> -- 'bash /workspaces/durakProekt/scripts/codespace-check.sh'
```

Ещё нюанс: у современного `gh` нет флага `--command` — команда передаётся
после `--`. Вариант `gh codespace ssh --command "..."` завершается с
`unknown flag: --command`.

Если SSH недоступен (например, `error getting ssh server details: failed to
start SSH server` сразу после создания codespace) — подождите 1–3 минуты:
фичи devcontainer (в т.ч. `ghcr.io/devcontainers/features/sshd:1`) и
`postCreateCommand: npm install` доустанавливаются уже после того, как
codespace получил статус *Available*. Альтернатива — веб-терминал
`https://<имя-codespace>.github.dev` или GitHub Actions
(`.github/workflows/ci.yml`).

## 8. Что делать с найденными проблемами

Заводите **отдельный issue** на каждую проблему и указывайте:

1. что запускали (точная команда и переменные окружения);
2. что ожидали и что получили;
3. вывод терминала / лог из тестового клиента (блок `#log`);
4. параметры партии: число игроков, размер колоды, `throwInPolicy`;
5. по возможности — номер шага из `game.log`, на котором всё разошлось.

Для воспроизводимости зависаний удобно прогонять `simulate.js` с большим
числом партий и указывать в issue, на какой конфигурации словили.

## 9. Как дорабатывать проект

- **Правила**: `src/rules.js` — дефолты, `src/game.js` — их применение.
  Любое изменение правила проверяйте `simulate.js` на всех комбинациях
  2–6 игроков × 24/36/52.
- **Боты**: `src/bots/simpleBot.js` — чистая функция
  `simpleBotDecide(state, playerId, legalActions)`, ничего не знает ни про
  сервер, ни про UI. Сильного бота можно писать рядом и подменять в
  `server/rooms.js` и CLI-скриптах.
- **Сервер**: `server/index.js` — только транспорт (HTTP/WS, парсинг,
  лобби-рассылка); `server/rooms.js` — комнаты, места, боты, очистка.
  Протокол сообщений описан комментарием в начале `server/index.js`.
- **Клиент**: `server/test-client.html` — отладочный, не финальный UI;
  финальный интерфейс планируется на базе `docs/index.html`.

Порядок работы: своя ветка → изменения → прогон CLI-проверок → ручной тест
сервера по разделу 5 → PR/отчёт в issue.
